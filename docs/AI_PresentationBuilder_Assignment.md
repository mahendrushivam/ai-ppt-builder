# Assignment

## Technical Assignment: AI-Powered Presentation Builder

### Background

Tools like [Gamma](https://gamma.app/), [Kimi Slides](https://kimi.com/), and [Tome](https://tome.app/) have changed how people create presentations. Instead of starting from a blank canvas, users describe what they want, and AI generates a first draft — which they then refine through conversation and manual edits.

We want to see how you approach building a product in this space.

## What You Are Building

A web-based AI Presentation Builder where a user can:

1. **Generate slides from a prompt.** The user describes a topic or provides an outline (e.g., “Create a 5-slide deck on our Q3 product roadmap”), and the AI generates a first-cut presentation — multiple slides with titles, bullet points or body content, and a coherent structure.
2. **Iterate on slides through conversation.** The user can ask the AI to improve or modify the deck in natural language — e.g., “Make slide 3 more concise”, “Add a slide about pricing before the conclusion”, “Change the tone to be more formal”, “Rewrite the bullet points on slide 2 as a comparison table”. The AI applies these changes and the user sees the updated slides.
3. **Edit slides manually.** The user can directly click into any slide and edit text, reorder slides, delete slides, or add a new blank slide — without going through the AI. Manual edits and AI-driven edits must coexist without one destroying the other.

### Core Loop

**Prompt → AI generates → User reviews → User asks AI to refine OR edits manually → Repeat**

## Technical Expectations

This is not “call an LLM and render its text output.” We expect a thoughtfully designed agentic system. The following are baseline requirements, not bonus points.

### 1. Structured Output with a Slide Schema

The AI must return slides as structured JSON conforming to a schema you design — not freeform markdown or plain text.

The schema should model:

- Slide type (title, content, two-column, comparison, etc.)
- Title
- Body content (bullets, paragraphs, tables)
- Layout hints
- Speaker notes

The schema is the backbone of the product — a bad one will make everything downstream fragile.

### 2. Agentic Tool-Use (Function Calling)

The AI must operate via tool calls / function calling, not a single monolithic prompt that returns the entire deck.

Define tools such as:

- `add_slide`
- `update_slide`
- `delete_slide`
- `reorder_slides`
- `change_layout`

When the user says “make slide 3 more concise”, the AI should call `update_slide` with the new content for that slide — not regenerate the whole deck.

The AI decides which tool to invoke based on the user's intent.

### 3. Diff-Based Edits (Targeted Patches, Not Full Regeneration)

When the user asks for a change, the AI must return a targeted patch — the specific slide(s) or field(s) to update — not a full regeneration of the entire deck.

Full regeneration destroys manual edits and is not acceptable.

The state model must support applying surgical updates to individual slides while preserving everything else.

## Scope & Requirements

### Must Have

- A chat interface where the user describes their presentation or asks for changes, and the AI responds by generating or modifying slides.
- A slide editor / preview panel that renders the current state of the presentation and allows manual editing (text content at minimum).
- Slide operations:
  - Add
  - Delete
  - Reorder
  - Edit individual slides manually
- The AI must work on the actual slide data — when it modifies slides, the changes appear in the editor in real time. Do not mock the AI integration.
- All four Technical Expectations above must be implemented:
  - Structured output
  - Agentic tool-use
  - Diff-based edits
  - Two-phase generation
- The presentation should be exportable (PDF, PPTX, or at minimum a printable HTML view).
- If full export is too ambitious, a clean print-to-PDF view is acceptable — but state this decision in the README.
- Streaming responses — slides appear one by one as the LLM streams its response, rather than a loading spinner followed by a sudden dump.
- Rich content on slides:
  - Images
  - Charts
  - Tables generated by the AI

### Nice to Have

Prioritize these if time permits:

- Slide themes / templates (let the user pick a visual style).
- Undo/redo across both AI-driven and manual actions (unified history stack).
- Context window management — smart handling of what gets sent to the LLM as conversations grow long (token limits, summarization).
- Multiple presentation projects (a dashboard listing saved decks).

### Explicitly Out of Scope

- Authentication is not required. You can use a single-user, no-auth model. If you add auth, it will not earn extra credit — spend that time on the core product instead.
- No backend persistence is strictly required. If you persist data in localStorage or IndexedDB, that is fine. If you want a backend, keep it minimal.

## Technical Guidelines

### Use AI to Build This Assignment

We encourage and expect you to use AI tools (ChatGPT, Claude, Copilot, Cursor, etc.) throughout the development process — for planning, coding, debugging, and design decisions.

This mirrors how our team works day to day.

However:

- You must understand every line of code you submit. If asked to explain a design decision or walk through a specific implementation during the review, you should be able to do so confidently.
- Do not mock the core product. Since you are allowed to use AI, we expect a complete, working, end-to-end implementation — not a prototype with stubbed functionality. The AI slide generation, the chat-based refinement, and the manual editing must all genuinely work.
- Build a real product, not a demo with hardcoded responses.

## LLM for the Agentic Part

- Use any LLM (Sarvam, OpenAI, Anthropic, Google, open-source models via Ollama, etc.) for the slide generation and refinement logic.
- The LLM must use function calling / tool use — not return the entire deck as freeform text from a single prompt.
- Define a tool set (add, update, delete, reorder) and let the model decide which to invoke.
- Design a slide schema (structured JSON) that the LLM returns and the frontend renders.
- The AI must be context-aware — it should know the current state of the deck (slide titles, content, order) when making changes, so it returns targeted diffs, not full regenerations.
- Include your API key handling safely. Do not hardcode keys in the repo. Use environment variables and document the setup.

## Tech Stack

- **Frontend:** React (Next.js preferred, but any React framework is fine).
- **Styling:** Any CSS framework or design system you are comfortable with.
- **LLM integration:** Any provider. Use their SDK or API directly.
- **State management:** Your choice. Keep it simple and appropriate for the problem.
